## 개념 정의

Befficient는 "이미 한 선택이 최선이었는가"를 검증하는 서비스로, 사용자가 실제로 한 행동(카드 결제, 부동산 구매 등)과 그 시점의 대안(다른 카드, 다른 매물)을 비교해 **놓친 가치(FOMO)를 금액으로 환산해 보여주는 카운터팩추얼 의사결정 엔진**이다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 기존 추천 서비스처럼 "무엇을 사야 하나"가 아니라 "이미 한 선택이 놓친 게 있었는가"에서 출발한다는 점이 본질적 차별점이다 ^[archive/2026-04-19-befficient-부동산-llm.md].

동일 문제의식이 처음에는 부동산 매물 검색/거래 서비스로 논의되었고, 현재는 카드 소비 데이터로 먼저 테스트 중이다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 예: 스타벅스에서 8,000원을 결제했을 때 "다른 카드를 썼다면 1,200원을 더 아꼈을 것" 같은 방식으로 손실을 계산한다 ^[archive/2026-04-19-befficient-부동산-llm.md].

## 제품 구조 (3단 파이프라인)

1. **과거 분석 (FOMO 계산)** — 실제 선택 vs 최적 선택을 비교해 금액화 ^[archive/2026-04-19-befficient-부동산-llm.md]
2. **패턴 학습** — 사용자가 어떤 카테고리에서 반복적으로 할인/타이밍을 놓치는지 파악 ^[archive/2026-04-19-befficient-부동산-llm.md]
3. **미래 최적화 (사전 추천)** — "앞으로 이 카드를 써라" 등 다음 행동을 추천하는 단계까지 가야 서비스로 성립한다 ^[archive/2026-04-19-befficient-부동산-llm.md]

단순히 손해를 알려주기만 하면 "후회 생성기"가 되어 재방문이 없는 앱으로 끝날 위험이 크므로, 반드시 코칭/개선 제안까지 이어져야 한다는 점이 강조되었다 ^[archive/2026-04-19-befficient-부동산-llm.md].

## 기술 원칙

- 계산 로직은 **룰 기반**이며 LLM에 판단/계산을 맡기지 않는다; LLM은 사용자 의도 파악과 결과 설명(자연어 인터페이스) 역할에 한정한다 ^[archive/2026-04-19-befficient-부동산-llm.md].
- 데이터 확보는 **마이데이터 사업자 API 호출을 통한 원클릭 UX**로 설계할 계획이다 ^[archive/2026-04-19-befficient-부동산-llm.md].
- 다만 마이데이터 인증은 온보딩 복잡도와 이탈 위험이 있어, MVP 단계에서는 카드 문자/스크린샷 등 더 가벼운 입력 방식으로 시작하고 이후 마이데이터로 이전하는 순서가 권장되었다 ^[archive/2026-04-19-befficient-부동산-llm.md].

## 수익 모델

레퍼럴(제휴 수수료)을 받지 않고, 대신 사용자에게 직접 소액 결제(예: 5,000원)를 받아 "놓친 혜택" 상세 결과를 보여주는 방식을 채택했다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 이는 "광고 없이 진짜 혜택을 보여준다"는 신뢰를 핵심 무기로 삼는 포지셔닝이다 ^[archive/2026-04-19-befficient-부동산-llm.md].

손실액 규모에 따라 가격을 차등화하는 A/B 테스트를 진행할 계획이다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 논의된 구조(추정, 확정 아님):
- 손실액 5,000원 미만: 무료
- 5,000~30,000원: 약 1,900원
- 30,000~100,000원: 약 3,900원
- 100,000원 이상: 약 5,900원
잃은 돈보다 결제액이 비싸면 전환이 안 된다는 심리적 제약을 고려한 설계다 (추정) ^[archive/2026-04-19-befficient-부동산-llm.md].

일회성 결제 후 "부동산·대출까지 평생 무료" 제공 아이디어도 논의되었으나, 원가 폭발과 과한 약속으로 초기 신뢰를 해칠 위험이 있어 "파운더 패스(Founder Pass)" 형태의 한시적 프리미엄으로 대체하는 방향이 대안으로 제시되었다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 장기적으로는 사후 분석보다 결제 전에 최적 카드를 추천하는 "사전 방지"형 구독 모델(예: 월 4,900원)로 넘어가야 리텐션이 생긴다는 점이 지적되었다 ^[archive/2026-04-19-befficient-부동산-llm.md].

## 확장 로드맵

카드 → 금융(대출/보험) → 부동산 순으로 확장하는 것이 현실적이라고 판단되었다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 부동산 버전은 원래 구상에서 "예산 10억, 강남, 실거주, 맞벌이 출퇴근 동선, 공원 근접" 같은 자연어 조건을 입력하면 매물 수집→실거래가 분석→공시가격 비교→대출 구조 설계→세금 계산→권리 분석→계약까지 자동 실행하는 의사결정 엔진으로 논의되었다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 다만 이는 한 번에 구현하기엔 금융·법·중개가 얽힌 고난도 영역이라, 먼저 "추천 엔진(계약 없음)" → "금융 연결(대출 리퍼럴)" → "거래 자동화(중개·계약)" 3단계로 쪼개야 한다는 결론이었다 ^[archive/2026-04-19-befficient-부동산-llm.md].

부동산 버전에서 참고한 데이터 인프라(대추가 공개 API 기반)로는 대법원 인터넷등기소의 등기부등본 열람, 국토교통부의 공시가격·시세 정보, 렌트홈의 임대사업자 등록 현황 등이 있으며, 이는 누구나 접근 가능한 "인프라" 레이어로 차별화 요소가 아니라고 평가되었다 ^[archive/2026-04-19-befficient-부동산-llm.md]. 실제 차별화는 이 데이터를 조합해 투자수익률 계산, 권리변동 분석, 시세 추정 같은 "해석 엔진"을 만드는 데 있다고 판단되었다 ^[archive/2026-04-19-befficient-부동산-llm.md].

## 리스크 및 검증 계획

- 계산 정확도가 틀리면 신뢰가 즉시 무너지므로, 카드 혜택 조건을 100% 반영하는 룰 엔진 정확도가 핵심 관건이다 ^[archive/2026-04-19-befficient-부동산-llm.md].
- 출시 전 랜딩 페이지 + 가짜 결과(fake door) 방식으로 결제 전환율을 먼저 검증하는 방법이 제안되었다 ^[archive/2026-04-19-befficient-부동산-llm.md].
- 현재 출시 전 단계이며 시장 반응 테스트를 진행할 예정이다 ^[archive/2026-04-19-befficient-부동산-llm.md].
